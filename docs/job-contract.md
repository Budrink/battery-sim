# Контракт вычислительной задачи, версия 1

Это **локальная граница worker ↔ C++/CUDA**, а не публичный HTTP API.
Сервис на Python/C# ставит задачи в очередь, выбирает GPU и запускает процесс.
Ядро не знает о пользователях, очереди, HTTP или ImGui. Старые `headless`,
probe-инструменты, UI, сценарии и их коды завершения не изменены.

## Запуск

Описание батарей/установки отделено от задания: [experiment-v1](experiment-contract.md).
Перед созданием job его нужно преобразовать в обычный scenario командой
`battery_sim_compile_experiment`. Worker получает готовый самодостаточный снимок,
не разрешает внешние ссылки на каталог моделей и не меняет их ревизии.

```sh
./scripts/ide-cmake.sh --preset dev
./scripts/ide-cmake.sh --build --preset worker
./build/dev/battery_sim_worker examples/jobs/reaction-chain.json --output /tmp/battery-attempt-001
```

Для отдельной поставки без UI используйте configure/build preset `server`;
бинарник будет `build/server/battery_sim_worker`. Он не требует DISPLAY,
GLFW, ImGui или OpenGL. `battery::job` — слой для будущей серверной обвязки,
но HTTP, очередь задач и авторизацию этот worker сам не реализует.

Каталог результата **не должен существовать**, его родитель должен существовать.
Повторный запуск не перезаписывает даже незавершённую попытку. Новая попытка получает
новый каталог и `attempt_id`. Глобальную уникальность и дедупликацию `job_id`
обеспечивает очередь/БД сервиса, а не файловый worker.

## Запрос

```json
{
  "schema_version": 1,
  "job_id": "experiment-42",
  "attempt_id": "attempt-001",
  "scenario_path": "scenario.json",
  "run_configuration": {
    "environment_mesh_scale": 1,
    "isothermal_batteries": false
  },
  "observations": { "interval_s": 1 },
  "progress_interval_wall_s": 1,
  "checkpoint_interval_wall_s": 30,
  "limits": { "wall_time_s": 3600, "max_steps": 0 }
}
```

Обязательны `schema_version`, `job_id`, `attempt_id`, `scenario_path`.
Пути относительно **файла запроса**, не cwd. ID — 1–128 символов, первая буква/цифра,
далее ASCII буквы, цифры, `_`, `-`, `.`. Неизвестные поля оболочки запроса отвергаются,
чтобы опечатка не превращалась в незаметно проигнорированную настройку.
Существующий формат самого сценария не ужесточается и не мигрируется.

Значения по умолчанию — как в примере, кроме checkpoint-интервала и wall-лимита:
они равны 0 (периодическое сохранение и лимит отключены). `max_steps=0` отключает
лимит **дополнительных принятых подшагов этой попытки**. При завершении, отмене
или достижении лимита checkpoint сохраняется независимо от периодического интервала.

Для продолжения добавляется `"restart_from": "previous/checkpoint.json"`.
Физический сценарий и `run_configuration` должны остаться теми же. Можно менять
ID попытки, пути, частоту наблюдения и эксплуатационные лимиты.
Продление длительности или изменение химии — уже новый физический контракт;
автоматически продолжать такой checkpoint версия 1 не разрешает.

## Наблюдение не меняет расчёт

Worker вызывает тот же `Simulation::advance()`, что и старый `run_to_end()`.
Он не меняет dt, историю ядра, частоту её записи, химию, материалы или контакты.
Наблюдения читаются с завершённых **внешних интервалов**. `interval_s` — минимальное
расстояние между наблюдениями, а не требование попасть точно на эту временную сетку.
Первая и последняя точки записываются всегда; время — фактическое, интерполяции нет.

SIGINT/SIGTERM запрашивает отмену. Она исполняется между внешними интервалами,
как и проверка лимитов/checkpoint: текущий интервал завершается целиком. Поэтому
step-бюджет может быть превышен на один внешний интервал, а wall-бюджет — также
на время инициализации, текущего интервала и финализации. Это **мягкие**, не жёсткие
лимиты. Максимальная задержка не обещается, если завис драйвер/GPU. Жёсткий таймаут
сервис обеспечивает завершением процесса; последняя незаписанная работа тогда теряется.
Такой выбор сохраняет сетку шагов и точное продолжение, не добавляя скрытых dt-ограничений.

## Выходы

`stdout` — NDJSON, одна JSON-запись на строку. Каждая содержит `schema_version`,
`job_id`, `attempt_id`, монотонный `sequence` и реальное `wall_s` этой попытки.
Типы: `started`, `progress`, `physical_event`, `checkpoint`, `terminal`.
До чтения корректного запроса ID могут быть null. Прогресс указывает расчётное
`time_s`, целевое `target_time_s` и число принятых подшагов; это не обещание ETA.
Читать stdout нужно непрерывно: переполненный pipe тормозит worker.

Артефакты попытки:

| Файл | Содержимое |
| --- | --- |
| `request.json` | Разобранный исходный запрос |
| `effective-request.json` | Явные настройки обвязки с применёнными defaults |
| `scenario.json` | Снимок исходного сценария; именно его читает loader |
| `provenance.json` | Версия сборки, сценарий и run-настройки физического контракта |
| `observations.ndjson` | Макросостояния всех объектов: ID, температура K, повреждение, режим, энергия J |
| `events.ndjson` | Физические события текущей попытки; при resume прежние события не повторяются |
| `checkpoint-N.bin` | Неизменяемое сохранённое состояние, только для совместимого ядра |
| `checkpoint.json` | Атомарно обновляемая ссылка на последний полностью записанный checkpoint |
| `result.json` | Итоговый статус, причина, времена, балансы, проверки ожиданий и ссылки на артефакты |

Наблюдения версии 1 — **макроуровень**, не полная запись 3D-полей/газопереноса.
Существующий формат visual replay и его инструменты оставлены отдельно и не изменены.
В будущем такой экспорт можно добавить как отдельный артефакт, не меняя ядро.

`result.json` записывается последним через временный файл и rename. Наличие температур
или checkpoint само по себе НЕ означает успешного завершения. При жёстком убийстве
процесса `result.json` может отсутствовать — это прерванная попытка, не успех.
Статус уже опубликованного результата не меняется из-за потери последнего stdout-сообщения.
NDJSON может содержать незавершённую последнюю строку при аварии: такую строку не читать.
Rename защищает от частично видимого JSON при остановке процесса, но **не обещает
сохранность при отключении питания**: fsync/долговременное хранилище — отдельная задача.

## Завершение и валидация — разные оси

| Exit code | Статус | Значение |
| --- | --- | --- |
| 0 | `completed` | Достигнут конец сценария |
| 1 | `failed` | Ошибка инициализации, расчёта или ввода/вывода |
| 2 | `invalid_request` | Неверный запрос/сценарий или несовместимый checkpoint |
| 3 | `rejected`, reason=`output_exists` | Каталог/файл результата уже существует, ничего не затёрто |
| 124 | `limit_reached` | Мягкий ресурсный предел, частичный результат и checkpoint |
| 130 | `cancelled` | Управляемая отмена, частичный результат и checkpoint |

Неправильные аргументы самой команды дают exit 2 и usage в stderr (без созданной попытки).
Остальные обработанные ошибки сообщаются JSON-событием; если удалось создать каталог,
пишется также `result.json`. При недоступном диске/pipe это, разумеется, не гарантируется.
Ошибка содержит `stage`, сообщение и последнее подтверждённое внешнее время (либо null).
Worker не пытается сохранить потенциально несогласованное состояние после ошибки солвера.

`validation.scenario_expectations.status` — `passed`, `failed`, `not_requested`
либо `not_evaluated` для неполного расчёта. Проверяются только уже существующие
ожидания propagated/runaway_order, **не соответствие экспериментальным кривым**.
Пример: расчёт выполнен, каскад отличается от ожидаемого → `completed`, exit 0,
но validation=`failed`. Дальнейший score калибровки считает отдельная обвязка.

Остатки энергетического/химического балансов возвращаются отдельно в джоулях.
Worker не заменяет физические проверки ядра и не объявляет произвольный остаток
«допустимым». Неограниченный допуск или обход строгих проверок сюда не добавлялись.

## Совместимость и безопасность

Checkpoint проверяется по версии, build ID, точному каноническому сценарию и
run-настройкам. Build ID вычисляется из исходников core/run/job, сборочных описаний,
компиляторов, конфигурации и CUDA-архитектуры, а не только Git HEAD: незакоммиченные
изменения тоже учитываются. Это консервативная совместимость, не переносимый ABI.
Сохранённые defaults сценария восстанавливаются только тем же совместимым loader;
`scenario.json` не выдаётся за развёрнутую сериализацию всех внутренних C++ структур.
Checkpoint после обновления несовместимого ядра отклоняется, а не мигрирует молча.

FNV-контрольные суммы ловят повреждение данных, **не обеспечивают криптографическую
аутентификацию**. Нельзя принимать произвольные checkpoint-файлы от публичного клиента.
Пути локальные и доверенные: worker не является файловой песочницей. Будущий сервис
сам материализует входные файлы в отдельном рабочем каталоге, проверяет права,
размер геометрии/сетки и квоты, ограничивает CPU/RAM/VRAM и выдаёт GPU через окружение
(например, `CUDA_VISIBLE_DEVICES`). Запрос ограничен 1 MiB, JSON сценария — 64 MiB,
checkpoint — 4 GiB; эти ограничения не заменяют ресурсную изоляцию.

## Где код и как проверить

- `native/job/src/contract.cpp` — разбор и версия контракта.
- `native/job/src/artifacts.cpp` — файлы и атомарная публикация.
- `native/job/src/runner.cpp` — жизненный цикл расчёта, наблюдения, результат.
- `native/apps/worker/main.cpp` — аргументы и обработка сигналов.

```sh
./scripts/ide-cmake.sh --build build/dev --target battery_sim_worker battery_sim_job_contract_test -j3
ctest --test-dir build/dev -R '^(cuda_job_contract|cuda_worker_cli|native_architecture)$' --output-on-failure
```

Тесты проверяют совпадение прямой траектории и worker, независимость от частоты
наблюдений, отмену/продолжение, реальные SIGTERM, несовместимые/повреждённые checkpoint,
лимиты, отсутствие GPU, неизменность прежнего результата и отдельный статус ожиданий.
