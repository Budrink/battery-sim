# Как устроен движок

Начинать чтение стоит не с CUDA-ядер, а с `Simulation::step` и схемы ниже.
Задача разделения — менять отображение и конкретный опыт, не переписывая алгоритм.

## Слои

```text
сценарий JSON / параметры опыта
             ↓
native/run ──→ Scenario ──→ native/core ──→ состояние и события
                                ↑                   ↓
                     команды step/reset     native/visualization
                                ↑                   ↓
                           native/apps ←── окно ImGui / запись
```

| Каталог | Ответственность |
| --- | --- |
| `native/core` | Физические законы, геометрия расчётных сетей, интегратор, CUDA, балансы, состояние и checkpoint |
| `native/run` | Чтение JSON, проверка входных полей, явные переопределения конкретного запуска |
| `native/job` | Версионированный контракт worker: задачи, наблюдения, checkpoint, результаты; не HTTP и не физика |
| `native/visualization` | Цвета, цилиндры, объёмный газ, OpenGL/CUDA interop, чтение записей; без эволюции физики |
| `native/ui` | Опциональный ImGui-модуль: аргументы запуска, окно, кнопки, камера, управление отображением |
| `native/apps/viewer` | Только точка входа, вызывающая `battery::ui::run` |
| `native/apps/calibration_monitor` | Окно наблюдения за внешним калибровочным процессом |
| `native/tools` | Headless-прогоны, экспорт, измерительные адаптеры, диагностика и бенчмарки |
| `native/experiments` | Отдельные исследовательские реализации газопереноса, не новый production-алгоритм |
| `scripts` | Генераторы опытов, подбор параметров, оценка ошибок, построение графиков |
| `data` | Параметры и результаты конкретных опытов, их происхождение и ограничения |

Зависимости односторонние. Ядро не включает заголовки UI или загрузчика сценариев.
Оно получает готовую структуру `Scenario`; её можно собрать без JSON.
`battery_run` зависит от ядра, но не от графики. `battery_visual_data` можно использовать
без окна. Только `battery_renderer` и `battery_cuda_visual` требуют OpenGL.

Публичный API ядра не содержит JSON. Внутри газового backend остаётся **приватная**
JSON-зависимость для аварийных диагностических снимков. Это не загрузчик сценария
и не источник физических параметров.

## Варианты поставки

Один репозиторий, три независимых набора целей:

```text
desktop:  viewer → battery::ui → renderer / visual_data → battery::core
                              → battery::run ──────────→ battery::core
server:   worker → battery::job → battery::run ─────────→ battery::core
core:     внешнее приложение ──────────────────────────→ battery::core
```

`battery::core`, `battery::run`, `battery::job`, `battery::ui` — CMake aliases
соответствующих библиотек. Desktop статически линкует UI с тем же ядром.
Никаких RPC, копирования состояния для сервиса или виртуальной диспетчеризации
в физический шаг не добавлено.

| Preset | Результат |
| --- | --- |
| configure `dev`, build `viewer` | Текущий ImGui/OpenGL интерфейс и монитор |
| `server` | Worker, headless CLI и компилятор контракта; без UI, визуализации, исследовательских инструментов и тестов |
| `core` | Только библиотека C++/CUDA; без загрузчика сценариев, worker и UI |
| `headless` | Совместимое имя минимальной server-сборки в `build/headless` |

В `server`/`core` CMake вообще не подключает графический модуль и не ищет/
не скачивает GLFW, ImGui, ImPlot, GLM, OpenGL, X11/Wayland. CUDA Toolkit остаётся
обязательным; JSON нужен даже ядру для приватных аварийных диагностик.
Доступ к дисплею для вычисления не нужен. На build-машине без GPU задайте явный
`CMAKE_CUDA_ARCHITECTURES` вместо `native`; для расчёта GPU по-прежнему необходим.

```sh
./scripts/ide-cmake.sh --preset server
./scripts/ide-cmake.sh --build --preset server
python3 scripts/check_minimal_build.py --build build/server --mode server

./scripts/ide-cmake.sh --preset core
./scripts/ide-cmake.sh --build --preset core
python3 scripts/check_minimal_build.py --build build/core --mode core
```

Три переключателя: `BATTERY_SIM_BUILD_RUNTIME`, `BATTERY_SIM_BUILD_VIEWER`,
`BATTERY_SIM_BUILD_TOOLS`. У core-only также выключен `BUILD_TESTING`:
существующий набор интеграционных тестов использует runtime. Для headless-тестов
можно включить `BUILD_TESTING` при VIEWER=OFF — вернутся CPU-адаптеры визуальных
данных и исследовательские тестовые библиотеки, но не графический стек.

Будущий HTTP/gRPC-сервис — отдельная обвязка над `battery::job` либо процессом
`battery_sim_worker` ([контракт](job-contract.md)): авторизация, очередь, квоты,
выбор GPU и доставка результатов не относятся к ядру. Сейчас это **не HTTP-сервер**.
Удалённый UI будет получать сериализованные снимки/артефакты, а не указатели GPU
из локального renderer. Текущий UI остаётся локальным frontend; сетевой клиент
ещё не реализован. Редактор опыта теперь находится в `native/ui/src/editor`:
документ/файлы, панели свойств и 3D-предпросмотр разделены. Его снимок проходит
через тот же run-adapter, а не редактирует состояние работающего ядра.

## Один физический шаг

Точка входа: `native/core/src/simulation/simulation.cpp`, метод `Simulation::step`.

1. Проверить параметры времени, ограничить шаг ближайшей границей наблюдения,
   конца расчёта или заданного события; подготовить команду нагревателя.
2. Вызвать `CudaSolver::step`. Сначала строится кандидат следующего состояния;
   подтверждённое состояние не заменяется до успешной проверки.
3. После принятия шага продвинуть часы, обновить макропараметры, события и историю.
   Наблюдатели получают уже согласованное состояние.

Для используемой раздельной тепловой/массовой схемы основная последовательность
находится в `native/core/src/simulation/mass_step.cuh`:

```text
подбор допустимого dt
  → предварительное разрушение оболочки и расход энергии на него
  → переоценка открывшихся связей и допустимости шага
  → теплообмен + локальная химия/электрический нагрев
  → газообразование, локальное выравнивание смеси, фазовый обмен
  → перенос массы/энергии/кислорода и R3 в газовой сети
  → обновление повреждений и проверка состояния
  → commit: замена подтверждённых буферов
```

Не всякий режим включает каждую стадию. Старые контрольные транспортные режимы
сохранены, а не молча удалены. Порядок операций, ограничения шага и уравнения
при структурном рефакторинге не меняются. Неудачная проба не должна оставлять
половину нового теплового состояния рядом со старым газовым.

## Где искать конкретную физику

В `native/core/include/battery_native` лежат типы и законы, доступные тестам;
в `native/core/src` — реализация и внутренние CUDA-фрагменты.

Обе стороны разделены по подсистемам: `simulation`, `model`, `thermal`,
`electrical`, `chemistry`, `mechanics`, `gas/transport`, `gas/mixing`, `io`.
Header-only ограничения лежат в `numerics`, внешняя граница — в `gas/boundary`.
Тесты повторяют это деление; инструменты разделены на `probes`, `gas`,
`benchmarks`, `recording`. [Карта исходников с точками входа](../native/README.md).

| Что нужно изменить/понять | Основные файлы |
| --- | --- |
| Состав состояния и коэффициенты | `model.hpp`, `cuda_solver.hpp` |
| Теплоёмкость, R1, зарядочный химпотенциал, R2 | `conversion.hpp`, `joule.hpp`, `reaction.hpp` |
| R3, кислород, газовая смесь | `gas_combustion.hpp`, `gas_local_reactor.hpp`, `reactive_transit.hpp` |
| Направленная тепловая связность | `state_geometry.hpp`, `constitutive.hpp`, `gas_thermal_contact.hpp` |
| Память направления газовых связей (опционально) | `gas_direction_memory.hpp`, `gas_direction_memory.cuh`; [закон и конфигурация](gas-direction-memory.md) |
| Дискретизация твёрдых тел и контактов | `thermal_mesh.cpp`, `shell.cpp`, `aperture_geometry.cpp` |
| Газовые объёмы и каналы | `mass_mesh.cpp`, `gas_mixing.hpp`, `gas_ambient.hpp` |
| Повреждения и раскрытие | `shell_opening.hpp`, `deterministic_aperture.hpp`, `leading_shell_step.cuh` |
| CUDA-теплоперенос | `solid_transport_kernels.cuh` |
| CUDA-источники и сборка состояния | `solid_reaction_kernels.cuh`, `cuda_step.cuh`, `mass_transfer_stages.cuh` |
| Газовый интегратор | `cuda_gas_transport.cu`, `batched_gas.cuh`, `averaged_gas.cuh`, `implicit_gas_mixing.cuh` |
| Выделение GPU-памяти и загрузка топологии | `solver_storage.cuh` |
| Сведение по батареям / наблюдения | `macro_reduction_kernels.cuh`, `observations.cpp` |
| Продолжение сохранённого состояния | `checkpoint.cpp`, `checkpoint_io.hpp` |

Общий адаптер называется `CudaGasTransport`; он обслуживает и Monte Carlo,
и детерминированный сетевой backend. Старое имя `CudaKawasakiTransport`
оставлено только alias для исходной совместимости. Численный метод задаётся
настройками `Scenario::gas_model`; исторические вложенные флаги этого POD
не переупакованы, чтобы не менять устройство GPU-состояния и checkpoint.

Рабочие структуры газового интегратора собраны в `gas_work_types.cuh`.
Четыре верхнеуровневых CUDA-модуля переноса/перемешивания сами объявляют namespace
и подключают зависимости; больше не требуется включать их внутри чужого namespace.
Внутренние фрагменты решателя давления и энтальпии пока остаются частями этих
модулей. Это не отдельные GPU-запуски: один translation unit, прежние inline-функции,
синхронизации и cooperative launch.

## Подготовка сценария — отдельно от расчёта

`native/run/src/scenario.cpp` задаёт порядок сборки, не содержит все парсеры:

1. `scenario/cells.cpp` — объекты и их исходные параметры.
2. `scenario/shells.cpp` — оболочки и обновление индексов объектов.
3. `scenario/thermal_links.cpp` — порты, теплообмен, нагреватели и внешние границы.
4. `scenario/gas_network.cpp` — газовые каналы и привязка химии к объёмам.

Общие законы читаются в `scenario/material_laws.cpp`.
Материальные ограничения ядра проверяются в `core/src/model/validation.cpp`:
отдельные функции для R1/R2, электрики и legacy-механизмов.
Эту проверку вызывают и JSON-загрузчик, и построитель сетки из прямого `Scenario`.
Поэтому неподдерживаемая смесь механизмов отклоняется до запуска CUDA.
Геометрические проверки остаются в построителе сетки; это не полная валидация
всех аспектов сценария одним вызовом.

Новый контракт собирается независимо: `contracts/experiment_contract.cpp` —
порядок действий, `contract_validation.cpp` — поля/каталог/наблюдения,
`contract_assembly.cpp` — экземпляры, электрические воздействия и газовые маршруты.
Документные проверки не подменяют ограничения физической модели.

## Минимальное использование

```cpp
#include "battery_native/run_configuration.hpp"
#include "battery_native/simulation/simulation.hpp"

auto scenario = battery::load_run("scenario.json");
battery::Simulation simulation(std::move(scenario));
while (simulation.step()) {
    // Читать simulation.cells(), events(), process_diagnostics().
    // Здесь нет ImGui, OpenGL или Python-интегратора.
}
```

Приложение с JSON линкуется с `battery_run`; приложение, самостоятельно создающее
`Scenario`, — только с `battery_native_core`. UI получает read-only снимок через
`capture_visual_frame`; CUDA-поле в нём заимствованное и действительно лишь до
изменения/уничтожения соответствующего состояния симуляции.

`RunConfiguration` меняет только явно запрошенные настройки запуска. По умолчанию
загруженные коэффициенты и сетка сохраняются. Для replay запрещено менять физику
и топологию: интерполяция записи относится только к отображению.

## Проверки и сборка

Для будущей очереди задач добавлен отдельный `battery_sim_worker`, без изменения
прежних CLI и UI. Формат задачи, статусы, отмена и продолжение описаны в
[контракте worker v1](job-contract.md). Он зависит от `battery_run`/ядра, не от графики.

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j3
ctest --test-dir build --output-on-failure

# Headless: не загружает GLFW, ImGui, ImPlot или OpenGL.
cmake -S . -B build-headless -DBATTERY_SIM_BUILD_VIEWER=OFF
cmake --build build-headless --target battery_sim_headless -j3
```

`tests/test_native_architecture.py` проверяет направление зависимостей.
`run_configuration` и `viewer_options` проверяют запуск без создания окна/GPU-контекста.
`scripts/check_native_refactor.py` сравнивает старый и новый probe на одной и той же
траектории, исключая только измеренное время исполнения. Число шагов, события,
температуры, газовые запасы и балансы должны совпасть точно.

Для проверки скорости используйте `--repeats 5 --warmups 1 --max-slowdown 0.05`.
Скрипт чередует старый/новый бинарники, проверяет физику каждого запуска,
считает медиану парных отношений времени. При большом разбросе возвращается
`inconclusive_noise` (exit 2), при замедлении сверх допуска — ошибка (exit 1).
Это измеренный допуск, не разрешение менять численный результат.
Замеры выполняются без параллельной сборки или других GPU-прогонов.
Регрессионный checkpoint не заменяет экспериментальную валидацию всей модели.

C++/CUDA форматируется по корневому `.clang-format`. Калибровочные архивы,
сценарии и бинарные записи не форматируются и не переписываются. Python-пакет
`src/battery_sim` — отдельная справочная/историческая реализация; production-прогон
и native UI используют `native/core`, не этот пакет.

Результаты проверок и известные старые падения тестов:
[исходный отчёт рефакторинга](refactor-checks-20261028.md) и
[журнал: проверка читаемости и скорости от 2026-11-07](model-development-journal.md).

Старые исследовательские отчёты описывают состояние модели на момент опыта.
Их пути `native/src` и `native/include` исторические; текущая карта приведена
здесь. Сами отчёты и происхождение калибровок при переносе не переписывались.
