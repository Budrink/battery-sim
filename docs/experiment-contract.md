# Контракт батареи и эксперимента

## Версия 2: вход редактора и сервиса

Исполняемый документ — JSON `format: "battery-sim.experiment", version: 2`.
[Схема v2](../schemas/experiment-v2.schema.json) переиспользует материальные
разделы v1; модель батареи остаётся `battery-sim.battery` v1. Ни физических
законов, ни сетки, ни калиброванных коэффициентов миграция не меняет.
Пример [editor-experiment.json](../examples/contracts/editor-experiment.json)
синтетический: одна батарея с явным подключением источника, **не калибровка**.

Общий для UI и headless API: `compile_experiment(json)` принимает v1 и v2.
`upgrade_experiment(json)` явно импортирует v1 в v2; повторный вызов для v2
сохраняет документ без изменения. Полный исходный v2 сохраняется в metadata
скомпилированного сценария, включая поля, для которых UI ещё не имеет формы.
Неподдерживаемая версия или неизвестное поле не отбрасываются молча.
Проверка не запускает симуляцию и не требует окна/GPU; окончательные ограничения
построителя расчётной сетки остаются при создании Simulation.

```bash
# Проверить и получить native-сценарий на stdout:
build/dev/battery_sim_compile_experiment examples/contracts/editor-experiment.json
# Явный импорт старого контракта; результат — v2, а не native-сценарий:
build/dev/battery_sim_compile_experiment examples/contracts/reaction-chain-experiment.json --upgrade-v2
```

### Порты и перемещение

Каждый `assembly.ports[]` в v2 обязательно содержит `frame: "local" | "world"`.
`cell_id` — владелец и получатель теплового контакта. В локальном режиме это
явно описанная батарея или пассивная деталь; `centroid_m` и единичная `normal`
заданы относительно её центра и осей. Компилятор применяет кватернион
`orientation_xyzw`, затем перенос (только к центру порта). Площадь не меняется.
Порты `world` фиксированы в мире; при импорте v1 получают именно этот режим,
чтобы старые контакты не сдвинулись. Контакты с автоматически создаваемыми
элементами оболочки пока используют world либо штатные vent bindings.

Это преобразование портов, не CAD-мэшер: перемещение объекта не создаёт
контакты с новыми соседями и не перестраивает газовые полости автоматически.
Ограничения native на ориентацию сетки/оболочки и цилиндрические аппроксимации
остаются прежними. Идентификаторы объектов/портов стабильны при редактировании.

### Электрическая схема

`assembly.electrical_circuit` содержит `mode`, `nodes` (ID электрических узлов)
и `branches`. Общий узел означает идеальное соединение проводом.

- Ветвь батареи: `id`, `kind: "battery"`, `cell_id`, `from`, `to`.
  `from` — положительный терминал, `to` — отрицательный; положительный ток
  течёт от from к to (зарядка). Это электрические терминалы, не тепловые порты.
- Источник: `id`, `kind: "current_source"`, `from`, `to`. Положительный ток
  также от from к to, поэтому в простом зарядном контуре источник направлен
  от минуса к плюсу батареи.
- `conditions.electrical_drives` сохраняет токи и, при наличии, измеренные
  напряжения **отдельных батарей**. `conditions.source_drives` задаёт токи
  источников по `source_id`: `current_a` либо `current_profile_a`.

`mode: "prescribed_currents"` проверяет ссылки, уникальность подключения
батарей и баланс токов в каждом узле на объединении всех узлов времени
кусочно-линейных профилей (вне диапазона значение крайней точки постоянно).
Допуск KCL: `1e-9 * max(1 A, сумма модулей токов узла)`.
Топология может описывать последовательное или параллельное соединение,
но **токи ветвей заданы, не вычисляются из сопротивлений**. Независимые
`voltage_limited_setpoint` в этом режиме запрещены: они нарушили бы баланс.
Батарея без drive имеет нулевой ток; drive вне объявленной схемы — ошибка.

Этот режим сохраняет заданные токи. Для автоматического распределения
используйте `solved_dc`, описанный ниже. Напряжение источника нельзя молча
присвоить каждой батарее; строгий UI-баланс ядра не изменён.

`mode: "unmapped_drives"` — честное сохранение старого задания токов без
известной схемы: nodes/branches/source_drives должны быть пустыми. Именно
так мигрируется v1. Редактор должен явно показывать, что схема не задана.

#### Автоматический расчёт: solved_dc

`mode: "solved_dc"` требует `reference_node` из `nodes`. Ветви батарей
дополнительно содержат явную постоянную `emf_v` (не выведенную из SOC).
Источник может иметь kind `current_source` или `voltage_source`;
его source_drive содержит соответственно постоянный `current_a` или `voltage_v`.
У батареи этой сети не может одновременно быть независимого electrical_drive.
Пример: [laboratory-demo.json](../examples/contracts/laboratory-demo.json).

Перед каждым тепловым prepare CUDA вычисляет сопротивления из текущей
температуры/состава внутренней сетки батарей, затем решает узловую электрическую
систему: `Vfrom - Vto = emf + I*R`. Пересчитываются токи, напряжения клемм,
локальный I²R-нагрев и доступный UI-бюджет для зарядки. На принятом подшаге R
заморожено, как и в прежнем тепловом интеграторе; отклонённый шаг не накапливает
электрическую энергию. Один дополнительный CUDA kernel только для сетевого
режима; пересылки R/токов на CPU каждый шаг нет. Scratch сети не требует
дополнительного динамического checkpoint-состояния.

Решатель проверяет KCL и суммарную мощность ветвей. Ограничение — 128 неизвестных
MNA и 512 ветвей; сингулярная/плавающая сеть отклоняется. Провода идеальны.
Новый режим пока зарядный: обратный ток батареи отклоняется, поскольку
разряд химического запаса ещё не замкнут этим электрическим контрактом.
Динамическая ЭДС, нестационарные источники, предохранители, авторазмыкание при
потере проводимости и сопротивления внешних проводов пока не реализованы.
Нулевой заданный ток неподключённой батареи не требует фиктивного напряжения;
при ненулевом токе и хранении химической энергии проверка UI остаётся строгой.

### Внешний нагрев

Это отдельная пассивная пластина с `role: passive`, собственной теплоёмкостью,
геометрией и постоянным резистивным законом. Мощность задаётся через I²R;
тепло приходит через `directed_geometry`-контакт к наружному порту оболочки,
а не напрямую в химический объём. При сознательном отсутствии оболочки
контакт относится к поверхности внутренности. UI-мастер создаёт эти блоки
явно; исходные параметры батареи не переписываются.

Два режима: постоянная мощность или существующий `conditions.heating_protocols`
с температурным ramp, feedforward, пропорциональной обратной связью, пределом
мощности и отсечкой по температуре/скорости нагрева. Температура датчика не
навязывается солверу: регулятор может только уменьшить/добавить мощность до
заданного предела. Ёмкость пластины и h контакта — открытые аппаратные допущения,
не новые калиброванные константы. Мастер пока требует осевую призму (в том числе
явную расчётную аппроксимацию цилиндра).

### Состояние редактора и файлы

Стартовая сборка `examples/contracts/module-4x4.json`: 16 призм 20×20×40 mm
(внутренность), оболочка 1 mm, шаг 24 mm и 24 изолирующие прокладки 2 mm.
Каждая прокладка — отдельный пассивный тепловой объект, соединённый с двумя
наружными портами оболочек. Геометрия демонстрационная, не новая калибровка.
Химия R1/R2/R3, испарение, тепловые свойства и повреждение оболочки перенесены
из сохранённого FSRI30-профиля: `examples/contracts/fsri30-material-preset.json`.
Масса, запас жидкости и теплоёмкость масштабируются по объёму внутренности;
удельные энергии и кинетика не меняются. Оболочка сохраняет толщину 1 mm этого
стенда, но использует свойства стального proxy исходного расчёта. Это не
экспериментальная валидация прямоугольной батареи. Электрические коэффициенты
остаются демонстрационными; источник выключен.
Цепь 4S4P, зарядный источник выключен; на боку B05 (-X) находится плёночный
нагреватель 0.2 mm с сохранённым профилем FSRI30: предел 30 W, задание 0.1 K/s,
FF=0 и Kp=0.19767037747050903 W/K, датчик на противоположной стенке (+X).
Снимок и происхождение: `examples/contracts/fsri30-heater-preset.json`.
Плёнка занимает часть зазора: ISS-B04-B05 имеет толщину 1.8 mm вместо 2 mm,
без изменения материала. Оранжевый Heater locator показывает положение
сквозь другие элементы, не физическую температуру. Начальная charged_fraction=1,
старение и повреждения нулевые. Внутри каждой батареи 27 газовых поровых объёмов,
по одному на тепловую ячейку, с вытеснением газа жидкостью и твёрдым веществом.
Каждая площадка верхней и нижней крышек выпускает газ из прилегающей внутренней
ячейки; слабый клапан радиусом 1 mm расположен по центру каждой из этих крышек.
Закрытый кейс 120×120×80 mm, стенки 2 mm, пространственная газовая
сетка с максимальным размером 20 mm. Более узкие зазоры не удаляются.
Генератор: `scripts/generate_laboratory_module.py --output examples/contracts/module-4x4.json`.
Полный headless-прогон: `battery_sim_worker examples/jobs/module-4x4.json --output NEW_DIRECTORY`.

### Кейс, газовая сетка и неоднородная оболочка

Вкладка **Case** добавляет/обновляет шесть физических стенок: внутренние размеры,
положение, толщину, плотность, удельную теплоёмкость, k по осям, повреждение,
контакты газа со стенкой/твёрдыми элементами и теплоотвод в наружную среду.
По умолчанию у нового кейса и стартового 4×4-модуля наружный теплоотвод выключен:
`ambient_h_w_m2_k = 0`, внешние тепловые границы отсутствуют. Пластиковые стенки
сохраняют конечную теплоёмкость и теплопроводность, нагреваются и обмениваются
теплом с газом; внешняя поверхность пластика адиабатическая, но через отверстия
газ может уносить энергию. Это не нулевая теплоёмкость стенки.
Положительное `Outside h W/(m2 K)` включает охлаждение; возврат к нулю удаляет
ранее созданные границы. Заданные пользователем ненулевые значения при импорте
не заменяются автоматически.
Ёмкость стенки вычисляется из объёма, плотности и cp. По умолчанию новый кейс
имеет круглое отверстие диаметром 20 мм по центру верхней крышки (для маленького
кейса диаметр ограничивается четвертью меньшего размера крышки). Старые документы
без отверстий остаются герметичными: импорт не меняет их граничные условия.
Твёрдые контакты между стенками кейса автоматически не добавляются.

**Case → Place openings with mouse** включает размещение: щелчок по стенке
создаёт отверстие, щелчок внутри имеющегося выбирает его. Перетаскивание вращает
вид. Доступны круг и прямоугольник; размер и координаты редактируются в мм,
предпросмотр обновляется автоматически. `New opening` снимает выбор, `Delete
opening` или общая Delete удаляет выбранное отверстие. Undo/Redo сохраняют
геометрию целиком. Запущенный расчёт не меняется до `RUN SNAPSHOT`.
При открытии вкладки существующее отверстие выбирается автоматически:
`EDITING <id>` означает немедленное редактирование его формы и размеров.
Только явный `New opening` переключает поля на заготовку, которая применяется
следующим щелчком по стенке. Ошибки размера/пересечения показаны рядом с полями.

Контракт хранит список `assembly.gas_meshes.<case>.openings`: `id`, `face`
(`±x/±y/±z`), `shape` (`circle`/`rectangle`), `center_m: [u,v]`, `size_m: [w,h]`.
Для круга оба размера равны диаметру. Координаты относительно центра кейса;
оси граней циклические: X → YZ, Y → ZX, Z → XY. Пересекающиеся отверстия,
выход за границы и перекрытие твёрдым предметом изнутри отклоняются.

Площадь отверстия аналитически распределяется между касающимися газовыми
элементами; к удалённым элементам оно не подключается. Используется существующий
консервативный `ambient_boundary`: отток/приток по перепаду давления, перенос
энтальпии и кислорода. Принудительное обновление газа равно нулю, поэтому при
равных давлениях постоянный приток воздуха не выдумывается. Параметры внешнего
резервуара задаются в `opening_ambient` (`pressure_pa`, `temperature_k`,
`oxidizer_mass_fraction`); по умолчанию 101325 Па, 298,15 K и 0,232.

Визуализатор вырезает соответствующую форму и рисует её контур. Из теплоёмкости
стенки вычитается удалённый пластик, газовый тепловой контакт учитывает оставшуюся
площадь. Геометрическая опора контакта остаётся прямоугольной, проводимость
взвешивается по действительной площади. Толщина прохода не разбивается на
отдельные газовые элементы: это отверстие с коэффициентом расхода, не CFD-канал.

`assembly.gas_meshes` — явная инструкция **host-компилятору контракта**, а не
визуальные metadata и не новый солвер. Она содержит ID шаблона газа, размеры
и положение полости, максимальный размер элемента, h газ—твёрдое/стенка и
коэффициент расхода проходов. Шаблон газа задаёт начальную плотность, состав,
температуру и R3; глобального смесительного резервуара после компиляции нет.
Компоненты сетки получают эту начальную плотность и состав.

Внутри кейса строится **равномерная декартова решётка**, затем из её элементов
вычитаются осевые прямоугольные тела. Шаг одинаков вдоль каждой оси; число
интервалов выбирается округлением вверх, чтобы точно покрыть размеры кейса.
Полностью занятые элементы не получают газового состояния. Частично занятые
хранят только свободный объём. Несвязанные полости одного элемента остаются
раздельными: иначе тонкая прокладка превратилась бы в скрытый газовый проход.
Соседние элементы соединяются по **открытому пересечению** граней, газ—твёрдое получает
порт на реальном пересечении поверхности. Даже прокладка тоньше шага сетки
блокирует сквозной газовый путь; огибание возможно только через свободное место.
Теплообмен идёт через существующий directed_geometry закон. Площади контактов
и свободный объём сохраняются при изменении размера газовой ячейки.

Ограничения первого мэшера: осевые тела; цилиндры используют уже объявленную
равнообъёмную призматическую аппроксимацию солвера, не точную криволинейную CSG.
Не более 5000 позиций решётки и 12000 геометрических фрагментов; слишком мелкая
сетка отклоняется явно. Внутренние поровые запасы газа батарей сохраняют свою
привязку к тепловым зонам; их состояние не заменяется наружным воздухом.
Выход каждого участка оболочки направлен в примыкающую ячейку по центру
участка/клапана; это локализованное истечение, не распределение струи по CFD.
Если выход упирается в твёрдое тело, компиляция сообщает ошибку, не телепортирует газ.
Итоговые числа/объёмы/площади находятся в `metadata.resolved_gas_meshes`, границы
газовых элементов для renderer — в `metadata.gas_volume_geometry`. `low_m/high_m`
задают регулярную опору, `fluid_fragments` — её свободные части для отрисовки;
`lattice_index` идентифицирует позицию решётки.

**Shell / vents** задаёт материал, k и закон повреждений каждой из шести граней
выбранной батареи, а также закрытую грань, разрыв, круглый клапан или ослабленный
периметральный шов. Общая модель остальных экземпляров не меняется. Порог
перепада давления, скорость раскрытия, работа разрушения и ослабление шва/клапана
передаются существующему механизму deterministic_aperture. Физическая грань
разворачивается в локальные площадки текущей тепловой сетки; клапан должен
целиком помещаться в одну площадку (иначе явная ошибка). Положение и радиус — mm
в UI, m в контракте. Смешение старого trailing rupture и нового leading aperture
в одном опыте солвер не допускает; старые сценарии не переводятся молча.
В стартовом модуле верхние и нижние крышки имеют ослабленные клапаны и начало
теплового повреждения при 450 K (около 177 °C); у боковин — 900 K (около 627 °C).
Порог целой крышки — 600 кПа перепада давления, клапана — 40% от него.
Это явно заданные демонстрационные прочности, не измеренные характеристики.
На боковых гранях не объявлены пути прорыва; их тепловое повреждение всё равно
считается по своему закону. Разрушение крышки не переносит повреждения на
соседние плиты. Вскрытие не назначено по времени.

Выбор: клик по батарее/прокладке/нагревателю; **Alt+клик** по кейсу. Перетаскивание
вращает сцену и не считается выбором. Скрытые объекты не перехватывают клик.

`metadata.visual_materials` сопоставляет material_id с `insulation` (коричневый)
или `thermal_conductor` (белый), `enclosure` (прозрачный кейс),
`unspecified` сохраняет прежнюю отрисовку.
Это представление, не физические коэффициенты: смена display-класса не меняет k.
Индивидуальный `metadata.visual_objects[object_id]` имеет приоритет над общей
меткой материала. В редакторе **Pad type** — уже физический пресет: изоляция
получает k = 0,06, теплопроводящая прокладка — k = 2 Вт/(м·К) по всем осям.
Меняется только выбранный объект; его k можно затем редактировать численно.
Это начальные значения для настройки, не паспорт конкретного продукта.
Теплоёмкость, повреждение и сопротивления контактов остаются заданными отдельно.
Действие записывается в `metadata.editor_changes` и поддерживает Undo/Redo.
У прокладок отдельные видимость/прозрачность, температура накладывается поверх
цвета материала. Повреждения отмечаются только на оболочках батарей, а не на
прокладках или содержимом. Холодная прокладка
показывает материал, поэтому смешанный цвет не нужно читать как точное значение
обычной температурной шкалы. Слой `Shell damage` показывает D только оболочки;
содержимое, прокладки и газ сохраняют температурную окраску. Статус R1/R2 и
выгорание остаются в численных показателях, но не перекрашивают целую батарею.
Прорывы показаны чёрными заполненными пятнами по локальному размеру раскрытия;
это визуальная отметка отверстия, не добавленная масса сажи или новый материал.

В Assembly форма выбранной батареи редактируется отдельным блоком: Prism —
ширина X, длина Y, высота Z; Cylinder — диаметр и высота Z, всё в mm.
Изменение автоматически применяет размеры и обновляет 3D. Оно
использует отдельную копию модели выбранного экземпляра, остальные батареи
не меняются; undo/redo и сохранение контракта сохраняют форму.
Для цилиндра явно записывается равная по объёму призматическая расчётная
аппроксимация, а renderer показывает цилиндр. Это не новый цилиндрический мэшер.
Масса, суммарная теплоёмкость и химия остаются заданными отдельно. Локальные
осевые порты батареи масштабируются; внешние полости, нагреватели, world-порты
и площади сопряжения с соседями требуют проверки после изменения размеров.
Окно редактора перемещается за заголовок, вращение сцены захватывает мышь
и не перемещает окно.

Предпросмотр автоматически отслеживает изменения черновика, включая Undo/Redo.
Частые правки объединяются в обновления с интервалом около 150 мс; сам расчёт
времени при этом не продвигается. Невалидный промежуточный ввод оставляет
последний корректный вид с явным сообщением об ошибке, без бесконечных повторов.
Панель действий закреплена над свойствами, кнопки переносятся при сужении окна.
`Refresh 3D preview` остаётся ручным повтором, но для обычных правок не нужен.
Уже запущенный расчёт не меняется: для него нужен новый `RUN SNAPSHOT`.

Газ отображается как смесь, включая исходный воздух: цвет передаёт температуру,
оптическая плотность — относительную плотность смеси с визуальным усилением.
Это не измеренная концентрация дыма/сажи и не отдельная метка происхождения газа.
Остывшая смесь не исчезает; прежний температурный фильтр доступен через
`Display range / geometry → Hot gas only (filter)`.
Визуализатор не рисует линии, хвосты или движущиеся сгустки вдоль газовых рёбер.
Сохраняются объёмная смесь, пространственный градиент температуры и смещение
объёмного рисунка по принятому переносу. Пауза фиксирует картинку; это не
восстановленная CFD-скорость.

Стандартный 4×4-модуль явно загружает ненулевое газовое перемешивание из
`fsri30-gas-transport-preset.json`: диффузивный и потоковый обмен, температурное
перемешивание и температурную зависимость связности. Это эффективные параметры
старого FSRI30-подбора как стартовое приближение для демо, не универсальные
свойства газа. Этот перенос параметров сам по себе не менял геометрию. Позднее
в дефолтный кейс добавлено описанное выше верхнее отверстие.

Прозрачность смеси задаёт `Gas opacity`. `Gas motion` отключает только смещение
объёмного рисунка, сохраняя `Gas mixture volumes`. Это изменение представления,
не физического переноса.

Физический документ: `experiment.json`. Необязательный sidecar: `editor.json`
с `format: "battery-sim.editor", version: 1`, `experiment_id`, камерой,
списком скрытых объектов и UI-owned `layout`. [Схема](../schemas/editor-v1.schema.json),
[пример](../examples/contracts/editor-state.json).
`validate_editor_document(editor, experiment)` проверяет привязку и поля;
его вызывают после проверки самого эксперимента. Sidecar не передаётся
солверу и не входит в идентичность checkpoint. Отсутствие/несовместимость
sidecar не должно мешать открыть физический документ с обычной камерой.

CSV измерений и профили-артефакты хранятся отдельно: ссылки измерений остаются
`artifact_id` + SHA256, без произвольных файловых include. Модели батарей
встроены снимками, нет неявного `latest`. Входные токовые профили в этой версии
встроены массивами; ссылка на CSV измерения сама не задаёт воздействие.

Редактор проверяет новый документ до замены открытого, сохраняет каждый JSON
через временный файл в той же папке, fsync и атомарную замену и запускает
неизменяемый снимок. Файлы опыта и sidecar не образуют общую транзакцию: опыт
авторитетен, несовместимый sidecar игнорируется. Sidecar называется
`<имя-файла-опыта>.editor.json`. При импорте native-сценария с вложенным исходным
контрактом предложено новое имя `.experiment.json`, чтобы не перезаписать
расчётный артефакт. Native без исходного контракта не преобразуется с потерей данных.

## Совместимый контракт v1

Это вход виртуальной лаборатории, **не HTTP API и не новый солвер**.
Модель батареи переиспользуется; опыт фиксирует её снимок, размещение,
начальные состояния и воздействия. [job-v1](job-contract.md) по-прежнему
отвечает за очередь, лимиты, отмену и checkpoint.

Рабочий пример: [reaction-chain-experiment.json](../examples/contracts/reaction-chain-experiment.json).
Это синтетический тест существующей R1/R2/R3, **не калиброванная батарея**.

## Разделение

| Раздел | Ответственность |
| --- | --- |
| `battery_models[]` | Материалы, форма, теплоёмкость, внутренние связи, R1/R2, электрические свойства, отдельная оболочка и клапаны |
| `assembly.batteries[]` | Экземпляры: точная ревизия модели, положение, начальное состояние, внутренний газовый объём |
| `assembly` | Пассивные детали, порты, тепловые контакты, газовые полости/каналы, назначения выходов клапанов |
| `conditions` | Внешние тепловые границы/охлаждение, нагреватели, ток и напряжение |
| `numerics` | Длительность, шаги, сетка батарей, численные ограничения реакций, явные геометрические аппроксимации |
| `measurements` | Наблюдения для сравнения: единицы, источник, привязка и неопределённость; не источники тепла |
| `provenance` | Что измерено, откалибровано или предположено, пояснение и источники |

В v1 `passive_cells`, `ports`, `interfaces`, `gas_network`, `boundaries` и
`heating_protocols` — **явный мост к существующим native-блокам**, без
переименования физических законов. R3, начальные запасы газа/O₂ и настройки
газового интегратора пока остаются внутри `gas_network`. Полное отделение
его численных полей и библиотека газовых смесей — не реализованная в v1 задача.

## Модель и экземпляр

Библиотечная запись: `format: "battery-sim.battery"`, `version: 1`, `id`,
`revision`. Схема: [battery-v1.schema.json](../schemas/battery-v1.schema.json).
Отдельный пример: [synthetic-battery-model.json](../examples/contracts/synthetic-battery-model.json).
В `contents` находятся `material_id`, существующие `thermal`, `conversion`,
необязательные `degradation` и `electrical`.
Теплоёмкость остаётся свойством узла/смеси, теплопроводность — законом связи.
Поддержана существующая `conversion.chemistry: "r1-r2-r3"`. Зарядка остаётся
отдельным процессом накопления химпотенциала за счёт электрической энергии,
не переименована в R1. Энергии и строгий UI-баланс не изменяются.

В модели запрещены ток опыта, начальная температура/доля реагента, ID внешней
полости и шаг расчёта. Для изменения физики одного экземпляра создайте другую
ревизию: неявных `override` нет. Одинаковые `id/revision` не могут иметь две
записи в одном опыте. Неизменяемость ревизий между заданиями — обязанность
сервиса каталога; локальный адаптер не является этим сервисом.

Каждый экземпляр явно задаёт `initial_state`:

- `temperature_k` и отдельно `shell_temperature_k`, если есть оболочка;
- `damage_fraction` пока только **0**: legacy-повреждение нельзя смешивать с R1/R2-составом. Это ограничение текущего ядра, не запрет физической деградации через R1;
- `aging_fraction` в смысле текущей native-модели;
- `precursor_fraction`, `charged_fraction`; их сумма не выше 1.

`charged_fraction` — **не автоматически SOC из даташита**, а доля зарядного
химического запаса текущей модели. Преобразование SOC/SOH требует адаптера;
исходные измеренные значения можно сохранить в `metadata`. `aging_fraction`
также не подменяет процент потерянной ёмкости. v1 задаёт однородное начальное
состояние батареи; неоднородное продолжение — через checkpoint, не по температурам.

`shell` — отдельный материал. `null` означает сознательное отсутствие оболочки.
`vents` содержит локальные клапаны: `id`, `port_suffix` (например,
`case:+z:outer`) и существующий закон `channel` с `kind: "rupture"`.
Порог давления, расход и повреждение остаются прежней физикой.
`assembly.vent_connections` связывает каждый клапан ровно один раз с явной
принимающей газовой полостью. Для батареи B компилятор получает, например:

```text
from: inside-B → port_id: B:case:+z:outer → to: cavity
```

Не создаются автоматически выходы наружу, контакты соседей или пути сквозь
прокладки. Дополнительные повреждаемые участки и свободные газовые пути
описываются существующими `gas_network.channels`. Тепловые интерфейсы и массовые
каналы остаются разными графами. Для инерции газовых каналов явно задаются
длины, направления и вязкость — [описание](gas-direction-memory.md).

## Геометрия и единицы

Расчётные единицы — SI: м, кг, с, **К**, Па, Дж, В, А.
Native `opening_pressure_pa` — порог **перепада** давления, не абсолютное
давление камеры. Начальный газ задаётся массой, объёмом и температурой,
не вторым независимо заданным давлением.

`geometry` — габариты внутреннего объёма до добавления толщины оболочки:
`prismatic/pouch: [x,y,z]`, `cylinder: [radius,height]` (**радиус**, не диаметр).
Ось цилиндра — Z, `pose.position_m` — мировой центр,
`orientation_xyzw` — нормированный кватернион. Порты сборки имеют явные мировые
координаты как в native-формате; изменение позы экземпляра не пересчитывает их.

Native CUDA пока не строит цилиндрическую тепловую сетку; автоматическая
оболочка требует осевой призмы. Нужен явный
`numerics.batteries.<id>.geometry_approximation` с `geometry` и `reason`.
Объём внутренности должен сохраняться с относительным допуском 1e-6.
**Это не гарантирует сохранения площадей поверхности и контактов**: их нужно
восстановить и проверить отдельно. Контракт не добавляет CAD-мэшер или
автоматический расчёт цилиндрических контактов. Исходная форма сохраняется.

Сетка — `numerics.batteries.<id>.divisions`, а не свойство химии.
Ненулевой `minimum_dt_s >= 0.005`; `0` сохраняет существующую native-семантику.
Неизвестные обязательные материальные параметры нельзя заменить `null` в
исполняемом снимке: явное предположение и его основания указываются в `provenance`.

## Воздействия и измерения

`electrical_drives` задаёт `cell_id`, либо `current_a`, либо `current_profile_a`,
при необходимости `voltage_profile_v` и `current_input`. Сопротивление через
drive менять нельзя. Модель с электрическим законом без drive получает
явный нулевой ток. Измеренная U/I-кривая в `measurements` сама не включает ток:
управляющий профиль помещается в `conditions` осознанно.

Принудительных `primary_failures` в новом контракте нет: компилятор создаёт
пустой список. Разрушение должно получаться из физики. Старый загрузчик
по-прежнему принимает старые native-сценарии с назначенными событиями.

У измерения есть `id`, `quantity`, `unit`, `mapping.status`:

- `unknown`: `cell_id` запрещён, расположение неизвестно;
- `hypothesis`: предполагаемая привязка к существующему объекту;
- `confirmed`: подтверждённая привязка к существующему объекту.

Привязка к объекту **не утверждает точное место спая и модель его отклика**.
v1 не добавляет автоматическую выборку локального поля. Для камеры или
неоднозначного датчика оставьте `unknown`, подробности — в пояснении.
Поддержаны температура (`K`/`degC`), абсолютное/избыточное давление (`Pa`),
ток (`A`), напряжение (`V`). `uncertainty.absolute` и `burst_absolute` —
абсолютные погрешности в единицах канала, не проценты от градусов Цельсия.
Это метаданные, **не автоматическое ослабление критерия валидации**.

Необязательный `data`: `artifact_id`, SHA256 файла, `time_column`,
`value_column`, `time_offset_s`. Время источника — секунды;
`t_sim = t_source + time_offset_s`. Адаптер не скачивает файл, не читает
произвольный путь, не проверяет его хеш и не интерполирует измерения — это
обязанности сервиса загрузки/сравнения. Ссылки на измерения не нужны ядру для расчёта.

## Использование

Схема опыта: [experiment-v1.schema.json](../schemas/experiment-v1.schema.json).
JSON Schema — для редактора/API. C++ дополнительно проверяет ссылки, объёмы,
владение газом и native-топологию. Полные проверки CUDA-меша/интегратора
остаются при создании Simulation: компиляция не доказывает устойчивость и
не является экспериментальной валидацией.

```bash
./scripts/ide-cmake.sh --build build/dev --target battery_sim_compile_experiment
build/dev/battery_sim_compile_experiment \
  examples/contracts/reaction-chain-experiment.json > /tmp/scenario.json
```

Команда только проверяет и печатает JSON. Не считает, не калибрует, не запускает
UI; ошибки — stderr и код 2. Результат подходит существующему headless,
визуализатору или `scenario_path` в worker job-v1. Viewer и headless теперь
также принимают исходный experiment-v1/v2 через общий загрузчик. Для worker
job-v1 передавайте скомпилированный scenario.
Для сервиса есть чистая C++-функция `battery::compile_experiment(json)`.
Python/C# может вызывать CLI: расчёт остаётся C++/CUDA.

В опыте нет `latest`, файловых include или ссылок на изменяемый профиль.
Все модели встроены снимками. Полный источник сохраняется в
`scenario.metadata.experiment_contract`. Worker сохраняет готовый scenario;
его contract identity учитывает снимок и сборку. Это консервативно: даже
изменение описания измерений может запретить resume. Для продолжения нужен
тот же снимок, а не заново отредактированный каталог.

Калиброванные профили и формат бинарных checkpoint сохранены.
Автоматической миграции архивных опытов нет; новый режим электрической сети
включается явно и не заменяет прежние измеренные воздействия.

### Удаление и копирование в редакторе

`Delete` на панели редактора или клавиша Delete удаляет выбранный объект из
черновика: батарею (с оболочкой и внутренними газовыми объёмами), прокладку,
нагреватель или отдельную стенку. Связанные порты, контакты, каналы и контроллеры
очищаются; данные наблюдений сохраняются с неизвестной привязкой. Undo возвращает
изменение целиком. Во время ввода текста/числа клавиша Delete объект не удаляет.
Предпросмотр обновляется автоматически; запущенный снимок не меняется.

Последняя батарея защищена от удаления: действующий контракт требует хотя бы одну.
Если после удаления нарушается проверка электрической сети или оставшихся
маршрутов, редактор сообщает причину и не применяет удаление. Он не переподключает
соседей и не создаёт автоматически выход газа наружу при удалении стенки.

`Duplicate element` работает для батарей и пассивных объектов. Копия смещается
на 40 мм по X; её положение и внешние контакты нужно проверить. Для батареи
копируются внутренние газовые объёмы и их каналы; соединения клапанов сохраняют
явные назначения. Для пассивного элемента копируются свойства и порты, но не
контакты с соседями. Общая библиотека материалов не изменяется.

### Закон контакта газа с оболочкой батареи

В `assembly.gas_meshes.<case>.battery_surface_connectivity_per_m2` можно задать
полный `directed_geometry` закон: `geometry_reference_logit`, background/active
conductance и их destroyed-варианты, `endpoint_damage_weight`. Численные значения
conductance здесь заданы **на квадратный метр**; компилятор умножает их только на
реальную открытую газу площадь. Таблица отклика газового конца по-прежнему берётся
из `gas_network.surface_connectivity`, обратное направление — из материала оболочки.

Этот закон применяется только к физическим панелям оболочек батарей. Он не открывает
газу путь сквозь прокладки и не изменяет контакты с кейсом, нагревателем или другими
пассивными элементами. Для них остаются `surface_h_w_m2_k` и `wall_h_w_m2_k`.
При отсутствии поля поведение прежнее. Изменение кейса в редакторе сохраняет поле.

Демо 4×4 использует FSRI-derived закон с холодным масштабом 20 Вт/(м²·К),
logit = −ln(59), background = 0,2 и active = 1188 на м². Это явный перенос
эффективного калибровочного закона, не универсальное свойство газа и не валидация
новой сборки. Размеры, теплоёмкости и внутренние контакты при этом не меняются.

### Отключение внешнего нагревателя

Во вкладке нагрева доступны `Cutoff temperature C` и `Cutoff minimum rise C/s`
в единой карточке нового или существующего нагревателя. В контракте
температура сохраняется в Кельвинах, скорость — в К/с. Скорость 0 отключает
проверку скорости: достаточно достижения температуры, в том числе при уже
горячем или остывающем датчике. При положительной скорости оба порога должны
выполняться одновременно. Срабатывание необратимо до нового запуска/сброса.

Постоянная мощность с cutoff использует тот же `HeatingProtocol`: нулевые
`ramp_k_per_s` и `proportional_w_per_k`, мощность в `feedforward_w`. Это не
температурный зажим и не новая модель теплообмена. Для существующего нагревателя
без контроллера переключатель `Temperature controller / cutoff` добавляет такой протокол,
сохраняя мощность. Указанный в карточке датчик определяет, чья температура
вызывает отключение. Изменения редактора применяются к следующему Run snapshot,
а не к уже работающей симуляции. Старые положительные пороги сохраняют прежнюю
семантику; калибровочные файлы автоматически не переписываются.

Вкладка `Models` — форма свойств материала, а не дерево JSON. Наверху всегда
доступно `Initial contents heat capacity [J/K]`: общая опорная теплоёмкость
содержимого одной батареи, без оболочки. Прямо под ним, без раскрывающихся секций,
находятся массы и удельные теплоёмкости реагирующего вещества и жидкости,
теплоёмкости продуктов реакции и живой баланс: вклад каждого компонента и
остаточная теплоёмкость прочего инертного содержимого. При реакции и потере вещества
ядро пересчитывает текущую теплоёмкость. Форма показывает минимально допустимую
опорную теплоёмкость для заданных запасов реагентов и жидкости. Оболочка имеет
собственные плотность, толщину и удельную теплоёмкость в `Shell material`;
переопределения отдельных граней редактируются в `Shell / vents`.

Ввод в `Models` хранится отдельно до завершения редактирования и успешной
проверки согласованности материалов. Некорректная теплоёмкость, например ниже
суммарной теплоёмкости запасов реагента и жидкости, остаётся в форме с ошибкой,
но не попадает в общий документ: другие элементы и их превью продолжают
обновляться. Исправление применяется автоматически. Незавершённый ввод можно
отменить кнопкой `Discard model input`; пока он есть, Save / Run недоступны,
чтобы незаметно не сохранить или запустить старые свойства.

Изменение модели действует на все экземпляры этой ревизии: их список показан
над формой. Выбор батареи в сборке/превью выбирает соответствующую модель.
Единицы отображения: °C, г, мм, А·ч, миллиомы, кДж/кг и кДж/моль; контракт
сохраняет исходные единицы SI. Просмотр не устанавливает значения по умолчанию
и не меняет скрытые расширенные законы. Их можно редактировать в отдельной
вкладке `JSON`. В узком окне редактор занимает всю ширину, а превью доступно
во вкладке `3D preview`.

Параметры каждого контроллера показаны непосредственно под его нагревателем:
датчик, начальная целевая температура (°C), темп нагрева (°C/мин), коэффициент
регулятора, базовая/предельная мощность и cutoff. Общего раскрывающегося массива
контроллеров во вкладке нагрева нет. Верхний блок `Place a heater` выбирает только
место установки (батарея и грань). Кнопка добавления сразу выбирает новый
нагреватель и прокручивает к его обычной карточке. Отдельной урезанной формы
начальных параметров больше нет. Карточка также содержит теплоёмкость,
начальную температуру нагревателя и коэффициент его явного контакта с батареей.
Изменение контакта масштабирует его проводимость, сохраняя зависимость от
температуры/повреждений и не затрагивая другие контакты.

При отключённом контроллере работает `Uncontrolled power W`. При включённом
контроллере это поле неактивно: используются `Base power W`, `Controller gain W/K`
и `Maximum power W`. `Initial target from sensor` позволяет оставить начальное
задание равным начальной температуре датчика или задать его явно в °C.

### Газовые зазоры и физические плиты оболочки

Равномерная газовая решётка задаёт фоновые ячейки, а препятствия — фактические
газовые подобъёмы. Объединяются только части, образующие прямоугольник в 3D
(прямоугольный параллелепипед), без обхода угла батареи. Соседние подобъёмы внутри
одного фонового кубика тоже соединены конечным каналом. `mixing_length_m` и
`inertial_length_m` измеряются между центрами фактических газовых объёмов, не
между центрами пустых фоновых кубиков. Метаданные содержат `fluid_low_m`,
`fluid_high_m`, `fluid_centroid_m`; прежние `low_m/high_m` описывают фон решётки.
Это исправление геометрии, а не новый коэффициент теплообмена или закон реакций.

Оболочка — шесть непересекающихся физических плит с общей внутренностью и
контактами по швам. В `shell.face_materials.<face>` теперь можно переопределять
`thickness_m`, `density_kg_m3`, `specific_heat_j_kg_k` вместе с материалом,
теплопроводностью и законом повреждения. Отсутствующие поля наследуют общий
материал оболочки. Теплоёмкость каждой плиты равна её собственному `rho*cp*V`;
геометрия углов учитывает разные толщины соседних плит без дублирования массы.
Толщина строго положительна; скрытого минимального значения нет.

Поля доступны в Shell / выбранная грань. Редактор отклоняет толщину, при которой
плиты пересекаются с другими элементами. Изменение одной батареи не меняет модель
остальных экземпляров. Сетка на поверхности остаётся численной дискретизацией
плиты, а не дополнительным материалом: температура и повреждения принадлежат
её собственным объёмам. Максимальное повреждение клапана больше не рисуется на
всей поверхности внутренности батареи; реальные плиты отображают свой локальный
ущерб. Прорывы и клапаны цилиндрического visual proxy используют тот же рисунок
раскрытия, перенесённый на круглый торец или боковую поверхность. Скрытие
вспомогательных плоских тел не скрывает их прорывы.

Новая газовая топология требует нового Run snapshot. Checkpoint старой топологии
нельзя считать состоянием новой. Старые скомпилированные эксперименты не переписываются.

### Согласованная сетка оболочки (2026-11-09)

Шесть объектов граней — это шесть материалов/макроплит, **не шесть расчётных
узлов**. Внутренность 3×3×3 по умолчанию окружена 54 тонкими плитками (3×3 на
каждой грани). Каждая плитка имеет собственные температуру, повреждение и
состояние раскрытия, если на ней задан разрушаемый газовый канал.

`numerics.batteries.<id>.shell_surface_divisions` задаёт целочисленно кратное
уточнение относительно `divisions`. Например, `[6,6,6]` при внутренней сетке
`[3,3,3]` даёт 216 плиток, а не 216 объёмов внутри батареи. По нормали к грани
всегда один слой. Некратное или более грубое разбиение оболочки отклоняется.

Внутренние линии разбиения оболочки точно совпадают с линиями внутренности
или их кратным уточнением. Дополнительные угловые полосы входят только в крайние
плитки; они не растягивают всю поверхностную сетку. Их теплоёмкость, площадь
раскрытия и работа разрушения рассчитываются по фактическим размерам. Один
приграничный внутренний объём может обслуживать несколько мелких плиток, но
плитка не объединяет разные внутренние объёмы обходным тепловым контактом.

Газовый источник и положение выхода назначаются по этой же сетке. Локальный
клапан должен помещаться внутри своей плитки; при уточнении, пересекающем клапан,
контракт выдаёт ошибку, а не переносит клапан в другое место. Визуализация поля
оболочки учитывает реальные центры плиток и границы разбиения. Для применения
изменённой геометрии нужен новый Run snapshot; старый checkpoint не переносится.

Для полностью описанной разрушаемой грани `deterministic_aperture` компилятор
контракта по умолчанию включает `whole_plate`: один связный фронт на физическую
грань, локальные температура и повреждения по плиткам. Это одинаково для
созданных в редакторе и импортированных батарей, независимо от формы.
Прочность, ослабление клапана, работа разрушения и маршруты газа не меняются.
Частичная апертура не создаёт отсутствующие пути газа; явное `whole_plate:false`
и готовые native-сценарии сохраняются для воспроизводимости старых расчётов.
Перекомпилированный контракт с новым общим фронтом — новая модель расчёта,
не подтверждение старой калибровки.

### Общая модель горения R3 и формы редактора

В начале вкладки **Models** находится **Global R3 combustion**. Это один закон
для всей газовой сети, включая автоматически построенные объёмы кейса и поры
батарей. Ни выбор батареи, ни разбиение сетки не ограничивают область действия.
Ниже отдельно редактируется материал батареи и его R1/R2.

Контракт хранит общий закон в `assembly.gas_network.combustion`:

```json
{
  "reaction_rate_per_s": 1.0,
  "reaction_reference_k": 600.0,
  "reaction_activation_j_per_mol": 40000.0,
  "oxidizer_heat_j_per_kg": 13100000.0,
  "ignition_temperature_k": 0.0
}
```

Это пример формата, не новая калибровка. Первые четыре поля обязательны;
отсутствующий или нулевой температурный порог означает отсутствие дополнительного
отсечения. В интерфейсе температура показана в °C, энергия активации — кДж/моль,
энергия на массу — МДж/кг; в файле остаются единицы SI. Энергия на килограмм
потреблённого кислорода — не удельная энергия топлива.

Общий закон имеет приоритет над прежними параметрами отдельных газовых объёмов.
Без него старые документы сохраняют прежнее поведение. Просмотр вкладки ничего
не меняет. Если в импортированном файле несколько разных законов, их замена одним
требует **Apply to all gas volumes**. Ошибочный ввод остаётся отдельным черновиком
и не блокирует редактирование других элементов; Save / Run требуют его исправить
или отменить.

Поле энергии испаряющегося топлива задаёт `gas_network.vapor_fuel_heat_j_kg`.
При общей модели оно также определяет химический запас жидкой фазы при сборке
расчётного состояния: до и после испарения это одно псевдовещество. Записанные
шаблоны батарей не переписываются. Теплоёмкость, теплота испарения, массы и
параметры R1/R2 от этого не меняются.

В обычных вкладках нет рекурсивных JSON-деревьев. Контакты, электрическая цепь,
охлаждение и численные настройки представлены отдельными подписанными формами.
Технический JSON остаётся отдельной вкладкой для расширенных импортированных
полей. Изменения редактора действуют на новый **RUN SNAPSHOT**, не на уже идущий
расчёт. Рабочий `module-4x4.json` автоматически не перезаписывается.

### Цилиндрические нагреватели

В Models / Model shape выбираются призма или цилиндр с размерами внутренности
(без оболочки). Правка модели применяется ко всем её экземплярам; Assembly
по-прежнему позволяет изменить только выбранный экземпляр. Для цилиндра
численная сетка остаётся равной по объёму призмой, изображение — цилиндром.

В Heating для цилиндра доступны Wrap around side, Top circular disk и Bottom
circular disk. У существующего нагревателя можно изменить монтаж в его карточке.
Обёртка контактирует с четырьмя боковыми гранями оболочки, диск — только с одним
торцом. Величина проводимости учитывает площадь `2*pi*r*h` или `pi*r*r`, где
размеры включают оболочку. Сохраняются общий источник мощности, регулятор,
теплоёмкость нагревателя и закон контакта на единицу площади. Изменяется сама
площадь/распределение контакта, поэтому прежняя калибровочная траектория не
является результатом новой конфигурации.

Обёртка — один изотермический тепловой объём; это огрубление тонкой плёнки,
а не четыре независимых источника мощности. У её контактов явно стоит
`lumped_heater: true`. Сборщик теплового графа распределяет проводимость по
площади плиток принимающей грани, сохраняет конечное сопротивление половины
плитки оболочки и использует обычный закон связности. Динамическая CUDA-схема
теплопереноса не меняется. Контакт запрещён для реагирующего источника или
источника с несколькими тепловыми объёмами. Численный компактный резервуар не
является полным цилиндром, вытесняющим дополнительный газ. Достоверная локальная
температура самой плёнки и её влияние на газовую геометрию остаются приближёнными.

`metadata.heater_mounts` связывает визуальную обёртку/диск с физическим
нагревателем. Обёртка открыта на торцах. Show heater в viewer и preview меняет
только видимость, не питание. После подтверждённого cutoff рамка становится
чёрной. Нулевая команда регулятора сама по себе не означает cutoff. Для старых
записей без сохранённого состояния регулятора cutoff не угадывается по температуре.

Отдельный вариант опыта: `examples/contracts/fsri30-shell-020mm-wrap.json`.
Его нагреватель B10 переустановлен с боковой пластины на обёртку; газовые
маршруты, химия, мощность и настройки регулятора сохранены. Предыдущий вариант
и защищённый `module-4x4.json` не изменяются.

### Отверстия созданных и импортированных кейсов

Вкладка Case использует общий список `editable_enclosures` и один инструмент
отверстий: круг/прямоугольник, размер, координаты, установка мышью на любой из
шести граней, удаление и Undo/Redo. Созданный кейс использует генерируемую сетку;
импортированный кейс с готовой сеткой регистрируется через
`register_explicit_enclosure`. Это общий контракт, не функция только для ABS/FSRI.

Для явной сетки нужны геометрия газовых объёмов, шесть стенок с обычными ID
`<case>-minusx` … `<case>-plusz`, исходные отверстия, их каналы и закон прохода.
Регистрация хранит обратимую редакторскую привязку в
`metadata.editor_enclosures`, не меняя физический снимок. Изменение отверстия
пересобирает только принадлежащие ему каналы по пересечениям газовых ячеек
с обеих сторон стенки. Существующий внешний газовый объём не заменяется
искусственным прямым выходом в атмосферу. Площадь газового прохода, тепловых
контактов и остающаяся теплоёмкость стенки учитывают вырез. Результат сохраняется
обычным физическим графом в контракте и не требует UI на сервере.

Совместимость со старым FSRI-импортом вынесена в отдельный адаптер: он восстанавливает
пропущенное описание кейса и координаты исходной внутренней газовой сетки.
Параметры, массы, газовые маршруты и нагрев при загрузке не меняются. Архивная
схема оставляла твёрдый ABS за дырой; после редактирования отверстий используется
согласованный вырез тепловых контактов, а возврат исходного списка восстанавливает
точный архивный вариант. Это геометрическая правка, не новая калибровка.

Размеры импортированного кейса пока заблокированы: произвольное изменение его
габаритов требует перестроения готовой газовой сетки. Это ограничение не мешает
создавать, перемещать и изменять отверстия. Теплопроводность и объёмная теплоёмкость
стенок доступны отдельно; плотность и удельная теплоёмкость не выдумываются, если
из импорта известна только их комбинация.
